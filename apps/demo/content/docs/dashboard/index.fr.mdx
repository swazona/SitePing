`@siteping/dashboard` vous donne une interface de tri complète : filtrer, rechercher, changer les statuts, supprimer, annuler — pensée pour le clavier, stylée pour se fondre dans votre app.

```bash
npm i @siteping/dashboard
```

```tsx
import { SitepingInbox } from "@siteping/dashboard";

// Une page d'administration de votre app, derrière sa connexion
export function Triage() {
  return <SitepingInbox projects="mon-projet" endpoint="/api/siteping" theme="auto" />;
}
```

Monté sur l'origine de l'endpoint, l'inbox envoie votre cookie de session avec chaque requête : protégez l'endpoint par une politique [`access`](/fr/docs/server#accès-personnalisé) qui réserve le tri à votre équipe. [Sources de données](/fr/docs/dashboard/sources#mode-endpoint-le-défaut-en-production) couvre les autres accès — un jeton dans `headers` depuis une autre origine, un store, une source personnalisée.

> **N'envoyez jamais l'`apiKey` au navigateur.** Elle autorise chaque changement de statut et chaque suppression : une variable `NEXT_PUBLIC_*` ou `VITE_*`, que le build inline dans le bundle client, la donne à quiconque ouvre la page. Ne passez `apiKey` que là où le code n'atteint jamais le visiteur : un outil interne sur un réseau privé, ou un script exécuté côté serveur.

Compatible React 18 et 19, livré en ESM et CJS, sans aucune dépendance en dehors de React. Le package porte sa propre directive `"use client"` : un Server Component peut donc rendre `<SitepingInbox />` directement, tant que chaque prop est sérialisable (`endpoint`, pas `store` ni `source`). Donnez-lui un conteneur avec une hauteur — l'inbox remplit son parent (minimum 480 px).

## Props

`SitepingInbox` accepte toutes les [options de `useSitepingInbox`](/fr/docs/dashboard/headless) plus ces props de présentation :

| Prop | Type | Défaut | Ce que ça fait |
|---|---|---|---|
| `theme` | `"light"` \| `"dark"` \| `"auto"` | `"auto"` | `auto` suit la préférence système — en direct, y compris quand elle change en cours de session |
| `accentColor` | `string` | `"#0066ff"` | Hexadécimal uniquement ; toutes les nuances d'accent dérivent de cette seule valeur. Voir [Personnalisation](/fr/docs/dashboard/theming) |
| `density` | `"comfortable"` \| `"compact"` | `"comfortable"` | Hauteur de ligne 44 px contre 36 px |
| `locale` | `string` | `"en"` | N'importe quelle étiquette BCP-47 — voir [Langues](#langues) |
| `deepLinkParam` | `string` | `"siteping"` | Paramètre d'URL utilisé par les liens « Ouvrir sur la page » ; doit correspondre au paramètre `deepLink` du widget |
| `emptyState` | `ReactNode` | — | Nœud personnalisé pour l'état « aucun feedback dans ce projet » uniquement — les états inbox-zéro et aucun-résultat gardent leurs valeurs par défaut |
| `className` | `string` | — | Ajouté aux classes de l'élément racine |

### Des pages sur une autre origine

Le widget enregistre la page de chaque feedback sous forme de chemin (`/pricing`) : « Ouvrir sur la page » et le lien de page du tiroir le résolvent donc par défaut contre **l'adresse de l'inbox elle-même** — ce qui est juste quand l'inbox tourne sur l'origine du site. Quand elle tourne ailleurs (une app d'administration, un autre sous-domaine), passez `siteUrl`, l'une des [options de `useSitepingInbox`](/fr/docs/dashboard/headless#options) : l'origine du site, ou une par nom de projet pour une inbox sur plusieurs sites. Un projet sans entrée garde le comportement par défaut, une URL de feedback absolue est gardée telle quelle, et un `siteUrl` qui n'est pas une URL http(s) absolue est ignoré avec un avertissement en console.

```tsx
<SitepingInbox
  projects={["client", "shop"]}
  endpoint="/api/siteping"
  siteUrl={{ client: "https://client.example.com", shop: "https://shop.example.com" }}
/>
```

## Clavier

Donnez le focus à la liste une fois, puis :

| Touche | Action |
|---|---|
| `j` / `↓`, `k` / `↑` | Se déplacer entre les lignes |
| `Entrée` ou `o` | Ouvrir le feedback ciblé ; un second `Entrée` sur un feedback ouvert l'ouvre sur la page en direct. Sur la ligne d'un [parcours](#parcours-sur-plusieurs-pages) : afficher ou masquer ses étapes |
| `→` / `←` | Afficher / masquer les étapes du parcours ciblé (`←` depuis une étape revient à la ligne de son parcours) |
| `e` / `p` / `x` | Basculer résolu / en cours / sans suite (appuyer sur le statut courant le remet à ouvert) |
| `u` | Annuler le dernier changement de statut |
| `r` | Actualiser |
| `/` | Aller à la recherche |
| `1`–`5` | Onglets de statut (tous, ouvert, en cours, résolu, sans suite) |
| `?` | Aide-mémoire des raccourcis |
| `Échap` | Dans la recherche : effacer la requête, puis quitter la recherche. Sinon : fermer le tiroir, puis l'aide-mémoire |

Les raccourcis exigent le focus à l'intérieur du composant (ils sont liés à lui, pas à `document`) et ne se déclenchent jamais pendant que vous tapez dans un champ — sauf `Échap`.

## Statuts et actions

Quatre statuts : `open`, `in_progress`, `resolved`, `wont_fix`. Le dashboard peut les définir tous (les actions du widget, elles, restent binaires : résoudre/rouvrir). Clore un feedback (`resolved` ou `wont_fix`) horodate `resolvedAt` ; le rouvrir l'efface. Les changements de statut sont optimistes avec annulation ; **la suppression est définitive** — elle passe par une confirmation en ligne et n'a pas d'annulation.

## Parcours sur plusieurs pages

Un [parcours](/fr/docs/widget/flows) — les commentaires d'un relecteur sur plusieurs pages — s'affiche sur une seule ligne : « Inscription · 3 étapes », avec ses auteurs, à l'heure de sa dernière étape, là où sa plus récente étape se placerait dans la liste. Cliquez-la, ou appuyez sur `Entrée`, pour afficher ses étapes juste en dessous, dans l'ordre, chacune avec son « Étape N » ; à nouveau pour les masquer.

Chaque étape reste un feedback à part entière : ouvrez-la, changez son statut, répondez-lui ou supprimez-la comme les autres — résolvez le code de vérification en retard et gardez ouvert le mauvais nom d'accueil. La ligne d'un parcours compte donc les étapes de l'onglet et de la recherche en cours : une fois l'étape 2 résolue, l'onglet « Ouvert » affiche « Inscription · 2 étapes », et l'onglet « Résolu » montre l'autre. Un parcours sans titre s'affiche « Parcours sans titre ».

Le regroupement est celui du composant : [`useSitepingInbox`](/fr/docs/dashboard/headless) garde `items` à plat, avec les `flowId`, `flowStep` et `flowTitle` de chaque enregistrement (depuis les serveurs qui parlent le [protocole 2](/fr/docs/server#parcours-sur-plusieurs-pages)) pour regrouper à votre façon.

## Enregistrements et chemins de composants

Ce que le widget a capturé avec un feedback s'affiche dans le tiroir :

- **Composant** — sur une page React, le [chemin des composants](/fr/docs/widget/configuration) de la racine jusqu'à l'élément annoté, en fil d'Ariane : `App › Layout › CheckoutForm`. Au-delà de quatre noms, son milieu se replie derrière un bouton `…` qui affiche le reste ; un nom long s'abrège seul, si bien que le composant annoté, en dernier, reste entier. Le bouton de copie met le chemin entier dans le presse-papiers, séparé par des `›`.
- **Enregistrement d'écran** — un [enregistrement](/fr/docs/widget/recording) se lit dans le lecteur du navigateur. La vidéo ne charge que ses métadonnées tant que vous n'appuyez pas sur lecture, et le lecteur lui-même est un chunk séparé (environ 1,3 kB gzippé), chargé avec le premier enregistrement ouvert. Sa durée, sa taille et un lien **Télécharger** se trouvent dessous ; quand le navigateur ne sait pas décoder le fichier, une ligne le dit et le lien de téléchargement reste. Un feedback sans enregistrement le dit aussi.

Une ligne avec un enregistrement porte une icône vidéo dans la liste.

Seule une URL d'enregistrement absolue en `http:` ou `https:` est lue ou liée. Le serveur ne garde que les URL que son `recordingStorage` reconnaît, mais un store peut contenir n'importe quelle chaîne — un autre appelant, une migration, une source personnalisée — : toute autre URL (`javascript:`, `data:`, un chemin relatif) n'entre jamais dans le lecteur ni dans un lien, et le tiroir indique qu'elle n'est pas affichée. Le navigateur traite **Télécharger** comme un téléchargement pour une URL de l'origine de l'inbox ; un stockage sur une autre origine ouvre la vidéo dans un nouvel onglet.

## Fils de discussion

Le tiroir montre le fil du feedback ouvert — les réponses du relecteur depuis le widget, celles de votre équipe depuis ici. Passez `author` pour répondre et supprimer depuis l'inbox :

```tsx
<SitepingInbox projects="my-project" endpoint="/api/siteping" author={{ name: "Alex" }} />
```

Sans `author`, les fils sont en lecture seule. Les réponses demandent le rôle `team`, que votre serveur n'accorde qu'aux appelants de confiance — les détails sont dans [Fils de discussion](/fr/docs/comments#dans-le-dashboard).

## Export

Le bouton d'export (la flèche vers un bac) transforme des feedbacks en rapport à coller dans un ticket, une discussion ou un agent de code IA. Dans l'en-tête du tiroir, il exporte le feedback ouvert ; dans la barre d'outils, les lignes que la liste a chargées — l'onglet, le filtre de type et la recherche en cours, sans les pages derrière « Charger plus » — avec une case par feedback pour en écarter.

| Format | Ce que vous obtenez |
|---|---|
| Markdown | Titres et listes ; chaque valeur fournie par le navigateur du relecteur en code |
| Texte brut | Le même rapport sans Markdown ; le message et les réponses derrière une gouttière `\|` |
| Prompt IA | Du Markdown présenté comme une tâche pour un agent de code : quoi chercher, où, et quoi rapporter |
| JSON | Le rapport en données — un objet, ou un tableau pour plusieurs feedbacks |

**Inclure** désactive des sections : page et élément (URL, sélecteur, XPath, texte de l'élément, la zone marquée, la fenêtre dans laquelle elle l'a été, le chemin des composants React quand le widget l'a relevé), navigateur et fenêtre, le lien de la capture, le lien de l'[enregistrement d'écran](/fr/docs/widget/recording), les erreurs et avertissements de la console (les autres niveaux n'y figurent jamais), les requêtes en échec, les réponses et l'auteur. Le message, le type, le statut et les dates y sont toujours, tout comme le [parcours](/fr/docs/widget/flows) dont un retour est une étape : son titre et le numéro de l'étape. Une capture intégrée est signalée, jamais incluse.

**Masquer** remplace ce qui ne doit pas sortir de l'inbox : jetons et clés (activé par défaut — jetons bearer, JWT, formats de clés Stripe, OpenAI, Anthropic, GitHub, GitLab, Slack, AWS et Google, et les valeurs des affectations et paramètres d'URL du type `token=` / `password:` / `api_key=`), adresses e-mail, paramètres d'URL, les noms de l'auteur et de tous les participants du fil, et le user agent. Le masquage repose sur des motifs : relisez un rapport avant de le partager.

Le prompt IA commence par dire à l'agent que tout ce qui est cité ensuite — le message, les réponses, les URL, le texte de l'élément, la console — est une donnée non fiable, pas une instruction. Chacune de ces valeurs est placée dans un bloc de code qu'elle ne peut pas refermer : un message rédigé pour ressembler à des instructions reste dans sa citation.

**Copier** met le rapport dans le presse-papiers (si le navigateur refuse, l'aperçu est sélectionné pour un `Ctrl`/`⌘`+`C`) ; **Télécharger** l'enregistre sous `siteping-<id>.md`, `siteping-<n>-feedbacks.json`, `-prompt.md` pour un prompt, etc. La boîte de dialogue se charge au premier usage : le premier chargement de l'inbox ne contient que le bouton. Pour confier des feedbacks à un agent sans copier-coller, voyez le [serveur MCP](/fr/docs/mcp).

## Lecture seule et permissions

`readOnly` masque les changements de statut et les suppressions, des feedbacks comme des réponses — pour une personne qui suit l'inbox, et répond quand `author` est défini :

```tsx
<SitepingInbox projects="my-project" endpoint="/api/siteping" readOnly />
```

L'inbox suit aussi ce que le serveur permet à chaque appelant sur chaque feedback — ses [`permissions`](/fr/docs/server#ce-que-chaque-appelant-peut-faire). Le tiroir affiche le statut en texte quand il ne peut pas changer et retire la suppression quand le feedback ne peut pas être supprimé, `e` / `p` / `x` passent un tel feedback, et les aides retirent les touches de statut quand aucun feedback listé ne permet de changement. Elle ne fait que masquer : c'est le serveur qui décide de ce qu'il accepte.

## Langues

Les mêmes locales intégrées que le widget (`en`, `fr`, `de`, `es`, `it`, `pt`, `ru`, `ja`, `ko`), l'anglais embarqué, le reste chargé à la demande, les étiquettes BCP-47 normalisées (`fr-CA` → `fr`), tout comme celles au format backend (`fr_FR` → `fr`).

Le dashboard accepte aussi des locales personnalisées à l'exécution :

```ts
import { registerLocale } from "@siteping/dashboard";

registerLocale("nl", { "status.open": "Open", "status.resolved": "Opgelost" });
// plus tard : <SitepingInbox locale="nl" ... />
```

**Les dictionnaires partiels sont acceptés** — sous un code intégré, les clés passées remplacent uniquement ces libellés et le reste du dictionnaire intégré est conservé (`registerLocale("fr", { "status.open": "À traiter" })` garde tous les autres libellés français) ; sous un nouveau code, toute clé omise retombe d'elle-même sur l'anglais. Dans les deux cas, corriger un seul libellé n'oblige pas à maintenir tout le catalogue, et les appels pour un même code s'additionnent. Deux règles que l'implémentation impose : enregistrez sous le **code de langue de base** (`"nl"`, pas `"nl-BE"` — les recherches se normalisent vers la base), et appelez `registerLocale` **avant le montage de l'inbox**. Le `registerLocale` du widget fonctionne de la même façon sur [son propre jeu de clés](/fr/docs/widget/i18n).
