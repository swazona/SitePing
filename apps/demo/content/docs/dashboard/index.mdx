`@siteping/dashboard` gives you a complete triage UI: filter, search, change statuses, delete, undo — designed for the keyboard, styled to blend into your app.

```bash
npm i @siteping/dashboard
```

```tsx
import { SitepingInbox } from "@siteping/dashboard";

// An admin page of your app, behind its login
export function Triage() {
  return <SitepingInbox projects="my-project" endpoint="/api/siteping" theme="auto" />;
}
```

Mounted on the endpoint's origin, the inbox sends your session cookie with every request: protect the endpoint with an [`access`](/docs/server#custom-access) policy that lets only your team triage. [Data sources](/docs/dashboard/sources#endpoint-mode-production-default) covers the other ways in — a token in `headers` from another origin, a store, a custom source.

> **Never ship the `apiKey` to the browser.** It authorizes every status change and every delete, so a `NEXT_PUBLIC_*` or `VITE_*` variable, which the build inlines into the client bundle, hands it to anyone who opens the page. Pass `apiKey` only where the code never reaches the visitor: an internal tool on a private network, or a script run server-side.

It works with React 18 and 19, ships ESM and CJS, and has zero dependencies besides React. The package carries its own `"use client"` directive, so a Server Component can render `<SitepingInbox />` directly — as long as every prop is serializable (`endpoint`, not `store` or `source`). Give it a container with a height — the inbox fills its parent (minimum 480 px).

## Props

`SitepingInbox` accepts every [`useSitepingInbox` option](/docs/dashboard/headless) plus these presentation props:

| Prop | Type | Default | What it does |
|---|---|---|---|
| `theme` | `"light"` \| `"dark"` \| `"auto"` | `"auto"` | `auto` follows the system preference — live, including mid-session changes |
| `accentColor` | `string` | `"#0066ff"` | Hex only; every accent shade derives from this one value. See [Theming](/docs/dashboard/theming) |
| `density` | `"comfortable"` \| `"compact"` | `"comfortable"` | Row height 44 px vs 36 px |
| `locale` | `string` | `"en"` | Any BCP-47 tag — see [Languages](#languages) |
| `deepLinkParam` | `string` | `"siteping"` | Query param used by "Open on page" links; must match the widget's `deepLink` param |
| `emptyState` | `ReactNode` | — | Custom node for the "no feedback in this project yet" state only — the inbox-zero and no-filter-match states keep their defaults |
| `className` | `string` | — | Appended to the root element's classes |

### Pages on another origin

The widget stores each feedback's page as a pathname (`/pricing`), so "Open on page" and the drawer's page link resolve it against **the inbox's own location** by default — right when the inbox runs on the site's origin. When it runs elsewhere (an admin app, another subdomain), pass `siteUrl`, one of the [`useSitepingInbox` options](/docs/dashboard/headless#options): the site's origin, or one per project name for an inbox over several sites. A project without an entry keeps the default, an absolute record URL is kept as stored, and a `siteUrl` that is not an absolute http(s) URL is ignored with a console warning.

```tsx
<SitepingInbox
  projects={["client", "shop"]}
  endpoint="/api/siteping"
  siteUrl={{ client: "https://client.example.com", shop: "https://shop.example.com" }}
/>
```

## Keyboard

Focus the list once, then:

| Key | Action |
|---|---|
| `j` / `↓`, `k` / `↑` | Move between rows |
| `Enter` or `o` | Open the focused feedback; a second `Enter` on an open record opens it on the live page. On a [flow](#multi-page-flows)'s row: show or hide its steps |
| `→` / `←` | Show / hide the steps of the focused flow (`←` from a step goes back to its flow's row) |
| `e` / `p` / `x` | Toggle resolved / in progress / won't fix (pressing the current status returns it to open) |
| `u` | Undo the last status change |
| `r` | Refresh |
| `/` | Jump to search |
| `1`–`5` | Status tabs (all, open, in progress, resolved, won't fix) |
| `?` | Shortcuts cheat sheet |
| `Esc` | In search: clear the query, then leave search. Otherwise: close the drawer, then the cheat sheet |

Shortcuts require focus inside the component (they're bound to it, not to `document`) and never fire while you're typing in a field — except `Esc`.

## Statuses and actions

Four statuses: `open`, `in_progress`, `resolved`, `wont_fix`. The dashboard can set any of them (the widget's own actions stay binary — resolve/reopen). Closing a feedback (`resolved` or `wont_fix`) stamps `resolvedAt`; reopening clears it. Status changes are optimistic with undo; **delete is permanent** — it sits behind an inline confirmation and has no undo.

## Multi-page flows

A [flow](/docs/widget/flows) — one reviewer's comments across several pages — shows as one row: "Sign-up · 3 steps", by its authors, at the time of its latest step, where its newest step would sit in the list. Click it, or press `Enter`, to show its steps right under it, in step order, each with its "Step N"; again to hide them.

Each step is still its own feedback: open it, change its status, reply to it or delete it like any other — resolve the late verification code and keep the wrong welcome name open. So a flow's row counts the steps of the current tab and search: once step 2 is resolved, the "Open" tab reads "Sign-up · 2 steps", and the "Resolved" tab shows the other. Untitled flows read "Untitled flow".

The grouping is the component's: [`useSitepingInbox`](/docs/dashboard/headless) keeps `items` flat, with each record's `flowId`, `flowStep` and `flowTitle` (from servers that speak [protocol 2](/docs/server#multi-page-flows)) to group your own way.

## Discussion threads

The drawer shows the opened feedback's thread — the reviewer's replies from the widget, your team's from here. Pass `author` to reply and delete from the inbox:

```tsx
<SitepingInbox projects="my-project" endpoint="/api/siteping" author={{ name: "Alex" }} />
```

Without `author`, threads are read-only. Replies ask for the `team` role, which your server grants only to callers it trusts — the details are in [Discussion threads](/docs/comments#in-the-dashboard).

## Export

The export button (the tray arrow) turns feedback into a report you can paste into an issue, a chat or an AI coding agent. In the drawer's header it exports the opened feedback; in the toolbar it exports the rows the list has loaded — the current tab, type filter and search, without the pages behind "Load more" — with a checkbox per feedback to leave some out.

| Format | What you get |
|---|---|
| Markdown | Headings and lists; every value the reviewer's browser supplied in code |
| Plain text | The same report without Markdown; the message and replies behind a `\|` gutter |
| AI prompt | Markdown framed as a task for a coding agent: what to look for, where, and what to report back |
| JSON | The report as data — one object, or an array for several feedbacks |

**Include** switches sections off: page and element (URL, selector, XPath, element text, the marked area, the viewport it was marked in, the React component path when the widget captured one), browser and viewport, the screenshot link, the [screen recording](/docs/widget/recording) link, console errors and warnings (other console levels never go in), failed requests, replies, and the author. The message, type, status and dates are always there, and so is the [flow](/docs/widget/flows) a feedback is a step of: its title and step number. An inline screenshot is noted, never embedded.

**Redact** replaces what should not leave the inbox: tokens and keys (on by default — bearer tokens, JWTs, Stripe, OpenAI, Anthropic, GitHub, GitLab, Slack, AWS and Google key formats, and the values of `token=` / `password:` / `api_key=`-like assignments and URL parameters), email addresses, URL query strings, the names of the author and of everyone in the thread, and the user agent. Redaction matches patterns: read a report before you share it.

The AI prompt opens by telling the agent that everything quoted below it — the message, replies, URLs, element text, console output — is untrusted data, not instructions. Each such value sits in a code span or a fenced block that it cannot close, so a message written to look like instructions stays inside its quote.

**Copy** puts the report on the clipboard (where the browser refuses, it selects the preview for `Ctrl`/`⌘`+`C`); **Download** saves it as `siteping-<id>.md`, `siteping-<n>-feedbacks.json`, `-prompt.md` for a prompt, and so on. The dialog loads on first use, so the inbox's first load carries only the button. To hand feedback to an agent without copying, see the [MCP server](/docs/mcp).

## Read-only and permissions

`readOnly` hides status changes and deletions, of feedbacks and of replies — for a stakeholder who follows the inbox, and replies when `author` is set:

```tsx
<SitepingInbox projects="my-project" endpoint="/api/siteping" readOnly />
```

The inbox also follows what the server says each requester may do with each feedback — its [`permissions`](/docs/server#what-each-requester-may-do). The drawer shows the status as text when it may not change and leaves out the delete when it may not be deleted, `e` / `p` / `x` skip such a feedback, and the hints leave the status keys out when no listed feedback allows a change. It only hides: the server decides what it accepts.

## Languages

Same built-in locales as the widget (`en`, `fr`, `de`, `es`, `it`, `pt`, `ru`, `ja`, `ko`), English bundled, the rest lazy-loaded, BCP-47 tags normalized (`fr-CA` → `fr`), and so are backend-style ones (`fr_FR` → `fr`).

The dashboard also accepts custom locales at runtime:

```ts
import { registerLocale } from "@siteping/dashboard";

registerLocale("nl", { "status.open": "Open", "status.resolved": "Opgelost" });
// later: <SitepingInbox locale="nl" ... />
```

**Partial dictionaries are accepted** — under a built-in code, the keys you pass override only those labels and the rest of the built-in dictionary stays (`registerLocale("fr", { "status.open": "À traiter" })` keeps every other French string); under a new code, any key you leave out falls back to English on its own. Either way, correcting a single label doesn't mean maintaining the whole catalog, and calls for the same code add up. Two rules the implementation enforces: register under the **base language code** (`"nl"`, not `"nl-BE"` — lookups normalize to the base), and call `registerLocale` **before the inbox mounts**. The widget's `registerLocale` works the same way against [its own key set](/docs/widget/i18n).
